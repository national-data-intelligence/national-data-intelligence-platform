# `bundle/seed-pack/app/security/` — convention guide

All seed YAML for the NHDW permission system lives here. The
loader at `7_security/scripts/load_security_seed.py` reads these
files in dependency order and idempotently INSERTs them into
`nhdw_ops`.

## Load order (mirrors FK dependencies)

1. **dashboards.yaml** → `ops_perm.dashboard`
2. **pages.yaml** → `ops_perm.page` (FK to dashboard)
3. **widgets.yaml** → `ops_perm.widget`
4. **filters.yaml** → `ops_perm.filter`
5. **mart_attrs.yaml** → `ops_perm.mart_attrs`
6. **identity_sources.yaml** → `ops_identity.identity_source`
7. **roles.yaml** → `ops_perm.role` + `ops_perm.role_capability`
8. **role_grants.yaml** → `ops_perm.role_dashboard` + `role_global_filter`
   + `role_widget` + `role_widget_filter`
9. **users.yaml** → `ops_identity.user` (upsert) + `ops_perm.user_role`
   (granted with source='admin_grant')

## When you add a new …

### …dashboard
- Add a row to `dashboards.yaml`.
- Add at least one page row to `pages.yaml` referencing it.
- Grant access in `role_grants.yaml` for at least R-OPS-ADM (otherwise
  no human can navigate to it).

### …page
- Add row to `pages.yaml`.
- Add widget rows to `widgets.yaml` for any new components.
- Update `role_grants.yaml` for every role that should see the page —
  remember: a role listed for the dashboard but not for the page lands
  on an empty section + `audit_silent_deny` row.

### …widget
- Add row to `widgets.yaml` with `requires` populated if it reads marts.
- Add a row to `mart_attrs.yaml` for any new mart it touches (otherwise
  the gateway OPA enrichment will fail-closed).
- Update `role_grants.yaml` for every role that should see it.
- Add a demo opportunity entry to `docs/demo-opportunities-log.md`.

### …filter
- Add row to `filters.yaml` with the right `source` enum.
  - `static` → put the full canonical list in `static_values`.
  - `mart_query` → set `source_ref` to a mart view; `static_values: null`.
  - `ops_db_query` → set `source_ref` to an ops-DB table/view.
- Reference the filter from `role_grants.yaml` under `global_filters` or
  `widget_filters` for each role that should see it.

### …role
- Add row to `roles.yaml` with `code`, `name`, `description`, optional
  `capabilities`.
- Add the matching grant block to `role_grants.yaml`. At minimum, list
  the dashboards the role can access; otherwise the resolver returns 404.
- For mart-backed widgets, ensure the corresponding `.rego` policy at
  `7_security/opa/policies/role_<code-lower>.rego` exists or the role
  will fail OPA enforcement.

### …user
- Add row to `users.yaml`. The loader upserts on `kc_sub`.
- Listed `roles` get inserted with `source='admin_grant'` so JIT logins
  from Keycloak don't overwrite them.

## `allowed_values` semantic (filter scopes)

In `role_global_filter` / `role_widget_filter` (YAML key
`global_filters` / `widget_filters`):

| Value | Meaning |
|-------|---------|
| `null` | wildcard — all canonical values from the filter catalog |
| `[]` | denied — the filter doesn't render at all |
| `["A","B"]` | explicit subset |

## Idempotency

Every loader UPSERT uses `ON CONFLICT … DO UPDATE`. Re-running the
loader on a populated DB is safe and updates everything to match the
YAMLs. The `audit_permission_change` rows generated by the loader carry
`actor_sub=NULL` and `revision_id=1` to distinguish bulk seeds from
admin-UI edits.

## Dumping the current DB back to YAML

After admin-UI edits land in production, run
`7_security/scripts/dump_seed.py` to refresh these files for the next
zip build. This round-trips the runtime state back into the canonical
source-of-truth.
